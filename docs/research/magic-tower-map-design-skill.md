# 魔塔地图设计规范

> 面向本仓库 `main/tower.c` 的十层塔（11×11），也适用于任何同规格的魔塔楼层。
> 数值与惯例的基准来自开源引擎 `ckcz123/mota-js` 与真实成品塔 `arcxingye/MagicTower`（胖老鼠 24 层），
> 布局原则来自 h5mota 论坛 tid=861 / tid=1028 的作者与玩家点评。
> 每条引用都标注了来源；标「未证实」的不作为硬约束。

---

## 0. 为什么需要这份规范

魔塔好玩与否，几乎完全由**地图**决定，而不是由战斗系统决定。战斗是确定的、
可预览的、不会失手的（见 `docs/research/gameplay-improvements.md` §1）。
玩家记得的是"我为了那把红钥匙绕了半个塔"，不是"我打赢了石魔"。

一份好的魔塔地图要同时做到三件事：

1. **让玩家做出选择**——同一层里"打怪"和"绕怪开门"是两条代价不同的路；
2. **让选择有代价且可承受**——代价要真实存在（血量、钥匙、步数），但不能一次选错就毁档；
3. **让玩家能预判**——���果在 1~2 层内就能看到，而不是 10 层后才发现"白开了"。

## 1. 地图数据模型

本仓库用 ASCII 字符表（`main/tower.c` 的 `initial_map`），这是小尺寸塔最省事的选择；
但**字符表只负责"放什么"，不负责"放多少"**，后者才是本规范的重点。

### 1.1 本仓库的字符表

| 字符 | 含义 | 类别 | 备注 |
|---|---|---|---|
| `#` | 墙 | terrain | |
| `.` | 空地 | terrain | |
| `U` / `D` | 上/下楼 | terrain | 切层后落到对侧楼梯格 |
| `G` | 目标（公主） | terrain | 顶层 |
| `y` `b` `r` | 黄/蓝/红钥匙 | item | |
| `Y` `B` `R` | 黄/蓝/红门 | door | 消耗对应钥匙 |
| `p` / `P` | 小/大血瓶 | item | +30 / +80 HP |
| `a` / `d` | 攻/防宝石 | item | +5 ATK / +3 DEF |
| `s` `v` `k` `X` `m` `g` `w` `M` | 史莱姆/蝙蝠/骑士/哨兵/法师/石魔/怨灵/魔王 | enemy | |
| `S` | 商店 | npc | |
| `n` | 对话 NPC | npc | |

### 1.2 参考引擎的层字段（若要迁到 mota-js 体系）

`ckcz123/mota-js` 的每层是一个 `project/floors/<id>.js`，目标 `main.floors.<id> = {...}`，
内容是 JSON5（容忍尾逗号）。必备字段：

```jsonc
{
  "floorId": "MT0",          // == 文件名，不能中文，区分大小写
  "title": "主塔 0 层",
  "name": "0",               // 状态栏楼层名
  "canFlyTo": true,          // 能否被楼传飞入
  "canFlyFrom": true,
  "defaultGround": "ground",
  "ratio": 1,                // 本层宝石/血瓶倍率
  "map":   [[/* 事件层 13x13 */]],
  "bgmap": [[/* 背景层 */]],
  "fgmap": [[/* 前景层 */]],
  "width": 13, "height": 13,
  "firstArrive": [], "events": {}, "changeFloor": {},
  "afterBattle": {}, "afterGetItem": {}, "afterOpenDoor": {}, "cannotMove": {}
}
```

## 2. 布局语言：六个可复用的配方

以下配方全部从 `arcxingye/MagicTower` 的真实 24 层数据里解析出来，标注了层号。

### 2.1 环廊 + 内嵌钥匙房 + 中心红门（MT7）

```
    0123456789012
  0 # # # # # # # # # # # # #
  1 # ▲ .. .. .. .. .. .. .. # # # #      ← 上楼点在左上角，走廊向右延伸
  2 # # # .. re # b # sk .. # # # #
  3 # # .. re bl # wh # re sk .. # #
  4 # .. .. # # #  s # # # .. .. #
  5 # .. .. b wh  s  cr  s wh b .. .. #   ← 中心红门
  6 # .. # # # #  s # # # # .. #
  7 # .. # h re #  wh # bl h # .. #          ← 环形夹层：红门↔蓝门↔黄门
  8 # .. # Y h #  b # h Y # .. #          ← 黄钥匙藏在最内圈
  9 # .. # # B B H B B # # .. #
 10 # .. .. # # # r # # .. .. #
 11 # # .. .. y ▼ .. .. y .. .. # #       ← 下楼点在底部
 12 # # # # # # # # # # # # #
```

- 外环 1 格宽走廊，起点（上楼，1,1）与终点（下楼，约 11,6）**分处对角**；
- 走廊内侧嵌一圈小房间，每间 1 怪 + 1 血瓶/宝石；
- 中心一扇红门 + 3 只高防怪；
- 黄钥匙放在内圈最深处：拿它必须先开 2 道黄门 + 打 4 只怪。

**设计意图**：上楼后被走廊"甩"到对角，必须沿环走一圈，每扇门都是一次"绕怪 vs 打怪"抉择。

### 2.2 中轴对称补给层（MT20）

```
    0123456789012
  0 # # # # # # # # # # # # #
  1 # M re wh h G R G h wh re M #
  2 # H st Y st B st B st Y st H #
  3 # st bl wh .. N .. N .. wh bl st #
  4 # h st Y st .. ▼ .. st Y st h #
  5 # G B N .. .. .. .. .. N B G #
  6 # R st .. st .. st .. st .. st R #
  7 # G B N .. .. .. .. .. N B G #
  8 # h st Y st .. ▲ .. st Y st h #
  9 # st bl wh .. N .. N .. wh bl st #
 10 # H st Y st B st B st Y st H #
 11 # M re wh h G R G h wh re M #
 12 # # # # # # # # # # # # #
```

楼梯 ▲(6,8) / ▼(6,4) 在**同一条中轴线上，相距 4 格**；全层 **20 把钥匙、0 扇门、28 只怪**。
这是前段"债务清偿点"——MT12–MT19 连续 8 层净消耗钥匙，MT20 一次回补 20 把。

### 2.3 三次元分裂隐藏层（MT22 → MT23L/R/D → MT24）

```js
main.floors.MT22 = { changeFloor: {
    "6,1" :{floorId:"MT21", stair:"upFloor"},
    "1,6" :{floorId:"MT23L", loc:[11,6]},      // 左岔路
    "11,6":{floorId:"MT23R", loc:[1,6]},       // 右岔路
    "6,11":{floorId:"MT23D", loc:[6,1]}        // 下岔路
} }
main.floors.MT23L = { name:"23", canFlyTo:false, ... }   // 三个子层同名同标题
```

四个要点（全部可从数据验证）：

1. 三个子层 `name` 都是 `"23"`，`title` 都是 `"主塔 23 层"` → **状态栏显示"23F"，玩家不知道自己在哪个分支**；
2. 三个子层 `canFlyTo:false` → 楼传进不去，必须靠楼梯进 → "不打这一层就拿不到东西"；
3. 从主层的**三个不同格子**分别进入 → **"上楼"这一个动作被拆成三条路径**；
4. 终局层无楼梯，只能靠事件 `changeFloor` 进入。

### 2.4 守卫房：门放在怪后面

```js
afterBattle: { "6,9": [ {type:"openDoor", loc:[6,8]} ] }
```

打怪 → `afterBattle` 开门。引擎文档点名一个经典 exploit：
**有阻击怪在场时，机关门守卫必须勾选「不可炸」**，否则玩家可以炸掉守卫、把阻击怪推过去打死来触发战后事件。

### 2.5 绕怪门（"咸鱼门"）

一个**功能上等价于无门**的门：门后不需要钥匙也能拿到等价收益。两种实现：

- `doorInfo.keys` 留空 `{"keys":{}}` → 永不开的门；
- 大黄门钥匙（`bigKey`）一键开本层所有黄门。

### 2.6 机关门 + 守卫

> 「简单地将机关门和守卫画在地图上，再右击机关门快速绑定」
> —— `mota-js/_docs/element.md`

## 3. 数值预算（十层塔）

基准：`arcxingye/MagicTower` 的 24 层主干 MT1–MT20 实测，缩放到 10 层。

### 3.1 钥匙-门经济

24 层实测（主塔 20 层）：

| | 黄 | 蓝 | 红 | 合计 |
|---|---|---|---|---|
| 钥匙总数 | **70** | 23 | **9** | **102** |
| 门总数 | 60 | 23 | **13** | **96** |
| K/D | 1.17 | 1.00 | **0.69** | **1.06** |

缩放到十层的目标值：

| | 黄 | 蓝 | 红 | 合计 |
|---|---|---|---|---|
| **钥匙** | 30 ± 5 | 10 ± 3 | **3 ± 1** | **45** |
| **门** | 27 ± 5 | 10 ± 3 | **5 ± 1** | **48** |
| K/D | 1.11 | 1.00 | **0.60** | 0.94 |

**红线规则**

- `红钥匙 < 红门` —— 保证"打不到的红钥匙"驱动回头。**这是整个魔塔最核心的一条数值规则。**
- `黄钥匙 ≈ 黄门`（K/D ∈ 0.9–1.3）—— 黄是主色，允许小幅盈余。
- 全塔 `总钥匙 / 总门 ∈ [0.90, 1.15]`。
- **单层** `钥匙数 ≥ 必开门数`（论坛原话），且 `钥匙数 ≤ 门数 + 2`。
- 钥匙/门的生产与消耗要**交替**出现，不要均匀分布：24 层 MT1–MT11 是钥匙层（K/D ≥ 0.8），
  MT12–MT19 是消耗层（K/D ≤ 0.33），MT20 一次性大补给。

### 3.2 血瓶、宝石、装备

24 层 `data.js` / `items.js` 实测：

| 道具 | 数值 | 效果 |
|---|---|---|
| 红血瓶 | 200 | `hp += 200` |
| 蓝血瓶 | 500 | `hp += 500` |
| 黄血瓶 | 500 | `hp += 500` |
| 绿血瓶 | 800 | `hp += 800` |
| 圣水 | — | `hp *= 2`（**生命翻倍**） |
| 红宝石 | 3 | `atk += 3` |
| 蓝宝石 | 3 | `def += 3` |
| 绿宝石 | 5 | `mdef += 5`（护盾） |
| 黄宝石 | — | `hp += 1000; atk += 6; def += 6; mdef += 10` |

- 血瓶阶梯 100/250/500/800 是**超线性**的：250→500 翻倍，500→800 只涨 60%。
- 蓝宝石（+3 防）数量 ≈ 蓝门数。
- 五级剑盾全塔只发一套。
- 参照比例：红宝石 +3 攻 = 3 级商店加点的 43%。

### 3.3 商店定价阶梯

24 层 `data.js` 原文：

```
金币商店 1F : 25 金币 → 生命+800 / 攻击+4 / 防御+4
金币商店 11F: 100 金币 → 生命+4000 / 攻击+20 / 防御+20
经验商店 5F : 30 经验 → 攻击+5 / 防御+5
经验商店 13F: 95 经验 → 攻击+17 / 防御+17
钥匙商店 5F : 黄钥匙 10 / 蓝钥匙 50 / 红钥匙 100
```

两条可直接照抄的经济学结论：

- **钥匙商店定价 10 : 50 : 100 = 1 : 5 : 10** —— 这条价格阶梯直接定义了"红钥匙最稀缺"。
- 金币商店从 25 涨到 100（×4），单次收益从 +4 涨到 +20（×5）——
  **单次变强 ×5 而价格只 ×4，单位收益上升 25%**，鼓励玩家回头买。

### 3.4 怪物

24 层 60+ 条怪物表的曲线规律（本次调研计算）：

- **`hp : def ≈ 3 : 2`**（skeleton 110/5、zombie 300/45、rock 500/65、slimelord 700/125、blueGuard 1250/400、slimeMan 3100/1050 全部落在这个带里）。
- **atk 增长慢于 hp**：greenSlime→vampire，hp ×600，atk ×85，def ×1500。
- **高层怪 def 逼近 atk**（slimeMan 1150/1050、redKing 1000/1000、vampire 1700/1500）——
  这让"打怪要靠回合数而不是秒杀"，从而产生血量消耗，也才有"要不要绕开它"的决策空间。
- 怪物密度：24 层 MT1–MT20 共 232 只，均值 **11.6 只/层**。

### 3.6 空间占用率

24 层 26 张 13×13 图实测：**空地 17.1%，墙 47.4%，其余 ~35% 是门/道具/怪/楼梯/NPC**。

| | 参考（24 层） | 本仓库（10 层） | 差 |
|---|---|---|---|
| 墙 | 47.4% | **74.4%** | **+27 pt** |
| 空地 | 17.1% | 15.6% | −1.5 pt |
| 物件（绝对占比） | ~35% | **10.0%** | **−25 pt** |
| **可走格中含物件的比例** | **67.5%** | **39.0%** | **−28.5 pt** |

**目标区间：墙 42%–52%，空地 12%–22%，物件 30%–40%，可走格中含物件的比例 ≥ 50%。**

> 注意最后一行才是关键诊断：本仓库的空地占比（15.6%）其实**达标**，
> 问题是**墙太多**（74.4% vs 47.4%），而剩下的可走格里只有 39% 放了东西
> （参考塔是 67.5%）。也就是说：**每层是一大片砖墙里嵌着一条细细的十字走廊，
> 走廊上还有六成是空地。**

### 3.7 「黑海」：魔塔不能变成什么（最权威的一份负面清单）

来自 h5mota 论坛 tid=1183《新人造塔避雷指南》3 楼（可酌露珠在一起）。
h5mota 的塔分五档：白 < 蓝 < 绿 < 橙 < **紫**。「紫」不是"难"，是**已经不是魔塔了**。
作者把"变成紫"的原因分成两大类：**黑海**（违背魔塔性质）与**数据**（布局/数值/属性问题）。

**黑海的五项性质**——每一条都是在说"这个设计让魔塔变成了另一种游戏"：

| 性质 | 含义 | 典型反例 |
|---|---|---|
| **技术性质「时空离散性」** | 魔塔不该有动作游戏式的**像素级**或**短于 1 秒**的高精度操作 | 空间上：pi-day-challenge 那种；时间上：玩家挂机但怪物和 NPC 依然走来走去 |
| **竞技性质「成绩有界性」** | 成绩必须**有上界** | 负伤血网、热卡血 |
| **竞技性质「完全重复性」** | 不要过多的局部随机 | 新新1 的史莱姆人 / 水银人 |
| **便利性质「信息透明性」** | 玩家该有的信息必须有 | 暗墙、隐藏层、陷阱、初见杀、不给手册、前景层恶意遮挡 |
| **便利性质「操作便捷性」** | 操作不该被故意拖慢 | 不给地图预览和显伤、不给楼传、强制低速移动/转场、强制大段不可快进过场 |

> 「时空离散性」是这一栏里最容易被忽略的：**它同时约束空间与时间两个维度**。
> 你的游戏在时间维度上很安全（回合制，一次一步，没有像素级操作），
> 但如果加入"实时走动的 NPC"就会立刻踩线。

**"数据"问题的三个子类**（见 §6.3、§6.4）。

### 3.8 减伤曲线：防御是线性的，攻击是"平移"的

tid=1183 3 楼（可酌露珠在一起）：

> 1. **减伤曲线问题**：防御力和护盾**线性减伤**，攻击力在不考虑临界（回合数不取整）的情况下
> **反比例平移减伤**，胖老鼠和新新一二以后的 rm 塔大部分都采取**怪物攻防和高于勇士**的做法
> 来防止无脑防杀（当然 flash 时代考虑到战斗过程，无脑防杀体验并不好）。

**这解释了"为什么要把怪物的 def 做得比玩家高"**——不是为了变难，而是为了让
"堆防御"这个无脑解法失效。本仓库的曲线形式恰好就是线性/平移（见 `tower.c`：

```
hit         = player_atk - enemy_def
retaliation = enemy_atk - player_def
```

**但数值上没有体现"怪物攻防高于勇士"**：玩家 DEF 上限 37，而后期怪物 DEF 到 46。
⇒ 后期防御完全失效，**堆防在后期不构成任何保护**，玩家被迫堆攻——
这既不构成"必须堆防"的设计张力，也不构成"堆防有风险"的代价，只是让 DEF 变成废属性。

### 3.9 血限、吸血、自爆

tid=1183 3 楼：

> 2. **生命、血限、吸血、自爆**：这几个放一起讲，我认为**无血限的高层塔原则上不要用样板的
> 吸血和自爆**，有血限的高层塔**不要全用即喝血瓶**而应该多用一些**便携血瓶**。

三条推论：

1. **无血限（HP 无上限）的高层塔** ⇒ 不该有吸血/自爆（否则玩家会自己把 HP 堆到天上，
   失去一切紧张感）。
2. **有血限的塔** ⇒ 血瓶不能都是"即喝型"（点击立即回满），要有一部分"便携型"
   （占用背包/格子、或需要走到某处才能用），让"回血"本身也有取舍。
3. 本仓库现在 **HP 无上限 + 22 个即喝血瓶 + 没有吸血自爆** ⇒ 第 1 条满足，
   但第 2 条无从谈起（因为根本没有血限，血瓶没有存在意义）。

### 3.10 结局、榜单、录像

tid=1183 3 楼：

> 3. **结局、榜单、录像**……首先是**随机性**，众所周知 rand2 是用户输入而 rand 是评论区求种子，
> 那么在「**不影响分数且不太影响通关成功率**」的前提下（比如高血量坚固怪加入暴击/闪避），
> 可以大胆尝试 `Math.random()`？
> 接着是**结局和榜单**，我个人非常推荐一种偷懒的做法就是「**连载塔分版本命名结局**」，
> 这样旧版本的榜单就不需要清理了。
> 最后是**录像**，有至少三种合法的录像操作是**无法人工稳定实现**的，分别是
> 「**停在楼梯上**」、「**非顺时针 90° 的转身**」、「**瞬移到相邻格**」，
> 因此**非常不建议通关路线对这三种操作有强依赖**。

**"连载塔分版本命名结局"是一个被低估的实用技巧**：给每一版地图一个独立的结局名
（例如"结局·塔顶" / "结局·真结局"），榜单天然按版本分区，不需要给旧榜单打补丁。

**录像的三种不稳定操作**（做通关录像/排行榜时必须避开）：

| 不稳定操作 | 为什么 | 本仓库 |
|---|---|---|
| 停在楼梯上 | 楼梯格的朝向/停留状态在录像里可能不一致 | **安全**——本项目切层是即时的，没有"停在楼梯上"这个状态 |
| 非顺时针 90° 的转身 | 转身动画的中间帧不可复现 | **安全**——格子游戏没有角色朝向 |
| 瞬移到相邻格 | 瞬移不是合法的一步 | **安全**——本项目只有四方向单格移动 |

> 换句话说：**格子化的回合制在录像复现上天然占优**。
> 这三条全是给有连续移动/朝向/过场动画的塔准备的。



论坛作者对"空"和"堆"的具体判据（tid=861 原文）：

> 4×4 区域只有两个怪/门/宝石的空会很难受（有非墙素材的装饰/boss 层除外），
> 堆满的地方达到 5×5 显得拥挤（击杀强怪的奖励区除外）。

## 4. 楼梯惯例

24 层实测：**23 层全部上下楼梯不同格，23/23 = 100%**。位移从 `(0,−2)` 到 `(10,0)` 不等。

| 层 | 上楼 | 下楼 | 位移 |
|---|---|---|---|
| MT1 | (1,1) | (6,11) | (+5,+10) |
| MT3 | (11,11) | (1,11) | (−10,0) |
| MT7 | (1,1) | (5,11) | (+4,+10) |
| MT8 | (7,5) | (1,1) | (−6,−4) |
| MT16 | (6,8) | (7,1) | (+1,−7) |
| MT20 | (6,8) | (6,4) | (0,−4) |
| MT22 | (1,6) | (6,1) | (+5,−5) |

> 「不对称放置」在 24 层是**硬事实（100%）**，但本次调研**没有**找到任何文档明文写
> "楼梯必须不对称"——这是从数据归纳出的惯例，不是规范条款。（未证实为文档条款）

功能意义：上下楼不同格 ⇒ 玩家每次切层都必须**穿越该层一次**。
同格则意味着原地上下折返，楼层变成纯过场。

**本仓库现状：10 层里 9 层的上楼梯固定在 `(5,1)`、下楼梯固定在 `(5,9)`。**
玩家每层都走同一条中央竖脊，地图失去了空间变化。

## 5. 复杂度度量

借用 h5mota 作者 gmh77 的方法（tid=1028）：

> 确定一个格子然后看**能到达它的有效路线数**（有效路线：代价相当，没有明显区别的路线）。

十层塔建议：3–5 层复杂度 2，3–5 层复杂度 3–5，1–2 层复杂度 ≥ 5。

配套的作者原话：

> **以宝石为锚，强度分区。** 先放红蓝宝石（和能力道具），根据宝石划分出**区域强度**：
> 绿 < 黄 < 红，一般按照和主路的距离近→远来由弱到强。
> 划分强度是为了让地图**更有纵深感，避免直接平推**。

> **血瓶看着放吧，在区域开头/强怪后面放多一些，区域中后期/怪物不强时少放一些。**

## 6. 反模式清单（含检测规则）

### 6.1 来自玩家与作者的批评

| 批评 | 原文/出处 | 检测规则（可脚本化） |
|---|---|---|
| **闲置怪** | 「红莱姆守着红宝石和血瓶，但是后面放了两个完全没有意义的绿莱姆」（tid=861） | 对守护同一资源节点的怪，计算各怪在玩家**所有可能属性点**下的损血。若存在怪 A 使对任意属性点都有 `损血(其他) ≤ 损血(A)` → A 闲置 |
| **同质怪并列** | 「放置了三种不同的怪物守着同一个红宝石，如果它们的伤害差距始终相似，那么玩家必然会选择打最弱的一个」 | 同一区域内 ≥2 种怪，其"每点防御减伤"和"回合数"同时相等 → 只需打最便宜的 |
| **傻瓜门** | 「如 1f 最上方的黄门与最下方的蓝门，是个人都不会开，要极力避免这种傻瓜门」 | 对每扇门做全塔寻路：是否存在一条通关路线经过它？不存在 → 傻瓜门 |
| **钥匙过剩全咸** | 「钥匙给的太多了，导致几乎所有门都能咸」 | 全塔最优路线下按颜色统计剩余钥匙；某色剩余 ≥ 该色门数 50% → 该色过咸 |
| **同房间双门同功能** | 「同一个房间有两个黄门，一个直接拿道具，一个要先打怪……那其中一个门就毫无用处」 | 同一资源点被两扇同色门守护且收益等价 → 冗余 |
| **卡钥匙 / 卡血** | 「杀光一整个区的小怪才发现被 boss 卡了血限，真的很难受」 | 对每层做资源可达性分析：站在楼梯点，用当前资源能否推进到下一个楼梯点？不可达且本层无可获取资源 → 卡死 |
| **决策反馈延迟** | 「如果我开了黄门，之后打了 N 层，被卡了黄才发现这个黄门不该开，那么这个决策的反馈就来得太晚了」 | 对每扇绕怪门，计算开它之后最快在哪一层会意识到开错；> 3 层 → 反馈太晚 |
| **无伤循环** | 「前中后期基本上都是拿几个宝石怪物无伤……这就导致看起来略有分歧的布局实际上毫无分歧」 | 模拟"当前属性 → 打完本层怪 → 拿到宝石 → 再打"：若损血恒为 0 → 该层无分歧 |
| **空气墙阻断路线** | 「用空气墙阻碍路线，无从寻找，路线之间让人无法分别是否可以通行」 | 存在"看得见但走不过"的可疑墙体 → 标注 |
| **满地地图伤害** | 「如果塔里的地图伤害普遍远小于怪物伤害，那么基本上可以认为这个地图伤害是可以删除的。地图上全是数字，玩起来就会很难受」 | 该层地图伤害 < 层内最小怪物伤害的 50% → 该层地图伤害无意义 |
| **空 / 堆** | 「4×4 区域只有两个怪/门/宝石的空会很难受……堆满的地方达到 5×5 显得拥挤」 | 滑 4×4 与 5×5 窗口，统计"有效物件"数；4×4 ≤ 2 → 过空；5×5 全满 → 过堆 |
| **楼层纯转换** | — | `怪数 == 0 && 钥匙数 == 0 && 门数 == 0` → 纯过场层（24 层里 MT15/MT18 属于剧情/宝箱层，是有意为之；其余属于浪费） |
| **无意义特技** | 「'伤害增加 10%'，就是一个几乎不影响决策空间的特技」 | 特技对最优打怪顺序的影响 < 某个阈值 → 移除 |
| **缺楼层传送** | 「没有楼层传送器是绝对让人恼火的设计」 | 主塔层数 > 15 且无任何传送手段 → 标注 |
| **门条件为"或"** | `doorInfo.keys` 只能表达"且" | 设计意图为"或"却未标注 → 警告（会丢自动存档） |
| **隐藏层可被楼传跳过** | — | 隐藏层 `canFlyTo == true` → 分歧失效 |

### 6.3 「堆水空」：审塔的拒发标准

tid=1052《拒发审核简易指南》（qweasz687，aka 堆水空指南）。
这是**审塔人真的会拿来做拒发依据**的三条：

#### 一、低质量水层过多

> 路线分歧楼层尽量在区域内不要出现很多，请尽量将路线设计丰富。
> （1）样例1：大量宝石，极少量怪物，玩家无脑走路
> 　注：请注意被圈出来的 **0 伤怪**，这些怪因为打不打无关紧要被称为**闲置怪**，
> 　　尽量不要让无意义的闲置怪物在你的塔内出现。
> （2）怪物较少或全是 0 伤，或者根本没有其他选择的情况
> 　……甚至还没拿完怪物已经基本上都没伤害了，请思考造塔的全过程，
> 　**保证正常流程下玩家至少需要多少权衡下自己拿取宝石的路线**。

**判据**：0 伤怪 = 闲置怪 = 该怪物的存在不改变任何决策 ⇒ 删掉它，或者把它调成有意义的。

#### 二、无脑堆叠过多资源的楼层，在区域内只应该占极少数或不存在

> 堆叠地图伤害（**领域，夹击，阻击，激光或血网**等）或类似负面属性或强制设置角色属性等
> 怪物属性（**中毒，衰弱，诅咒，自爆，退化**等）包括毒网衰网等。
> 如果要加入以上及类似属性，**请确保你的目的，然后多为你的玩家的体验想一想**。

#### 三、布局讲究恰到好处、错落有致，堆不行，太空也不行

> （1）总体布局太空 —— 空的问题一个在于并不好看，另一个本质问题则还是在
> 　　 **路线分歧即复杂度**问题上……问题的本质还是在于复杂度所反馈的游戏内容是否充实
> （2）无意义的局部空缺处
> （3）**大量使用对称进行水层** —— 对称是绘制地图的一种常见手段，但也是**水层手段**，
> 　　纯对称楼层在一个区域内应不要出现太多。同时**适当更改对称地图反而能发挥出
> 　　对称破缺的美感**。

> "专门为反例临时制作的拙作，本层基本对称但是做了很多对称破缺的地方，
> 其实只是四个角一边一个房间的对称风布局但是并没有带来劣质感"

**"堆"的严重性排序**（tid=1183 3 楼）：

```
堆怪（包括闲置） < 堆道具 < 堆门 < 堆空地（空） < 堆墙
```

> 严格来说在有金经的塔尤其是加点塔里堆怪和闲置怪不一定是坏事，
> 在有反制属性的塔里堆道具也不一定是坏事，**但其他三种确实意义不明**。

> 「堆一大堆门容易数不清楚一共有多少扇，**不如用事件同时配合数字图块提示所需钥匙数量**」

### 6.4 怪物技能的反制三档（决定"繁而不难"还是"难"）

tid=210《如何造爽塔》（水塔製作員）：

> 有不少常见���怪物技能都是**反制玩家属性**的。我个人把这些分为
> **弱反制、中反制、强反制**。

| 档位 | 定义 | 例子 | 玩家感受 |
|---|---|---|---|
| **弱反制** | 削弱某些属性的**收益**，但仍为正收益 | 怪物防御增加玩家攻击力的 10%；0.5 倍净化 | 「还是变强了，只是慢一点」 |
| **中反制** | 某些属性增加**无收益**（不是正也不是负） | 魔攻、坚固、1 倍净化 | 「这个属性白给了，但不恶心」 |
| **强反制** | 某些属性增加会导致**负收益** | 自爆、夹击、高倍反击、破甲、净化、吸血、窥血为攻 | 「**让玩家干什么都觉得自己在变弱**」，失去能力上升的快感，甚至要去抠抠该不该捡地上的物品 |

> 强反制属性「让玩家干什么都觉得自己在变弱」，令玩家失去能力上升的快感。
> ——这些属性"**令玩家感到恶心**"。

**还有一类是「固伤怪」**：

> 固伤怪，就是**不管玩家怎样做，伤害都是那个样子的**，例如：固伤（废话）、坚固+魔攻。
> 一样的，这些怪物令玩家感觉不到自己在变强，影响体验。
> **还有绝大多数塔的领域、阻击、激光也是一种"固伤"**。

**这条是"战斗有没有意义"的判据**：
如果玩家无论怎么加点，伤害都一样，那这个战斗就不是一个决策点。

**反制属性的两条戒律**（tid=1183 3 楼「属性问题『繁而不难』」）：

> 强反制属性（吸反破净爆）和耗散属性（**阻激夹域毒**）的存在意味着对于萌新的劝退，
> 而本站的非萌新又有着「易通关的塔不去刷榜」的坏毛病，因此使用这类属性
> **请务必找厉害的测试员卡好血**（一言以蔽之，请做好【**非红即紫**】的准备）。
> 讽刺的是，**卡血反而是在帮玩家尽早剪枝**。

**新人向的两条红线**（tid=210 1 楼，巴别塔的猪灵）：

> 千万不要【每区结束后提升全塔宝石/血瓶收益】
> 以及【强制夹击】【强制自爆】【强制高倍率吸血】等。
> 如果真的要面向新人玩家还要让新人控血，像魔方6那样【**夹击-80%**】或一夜登天那样
> 【**低难度地图伤害无效 / 可以使用技能反制**】都是不错的选择。

### 6.5 四种「卡」与「迪」

tid=210《如何造爽塔》：

> 这里的"卡"不只是指卡血，还有**卡属性、卡经验、卡门**等等……
> 每一种都会大大减低塔本身的容错，**玩家一但被卡容易感到绝望**，
> 不是去重打就是直接把塔关掉。

| 卡 | 定义 | 例子 |
|---|---|---|
| **卡血 / 卡血限** | 打怪时血不够 | 星云大陆：不小心中了一下毒，然后就没有然后了 |
| **卡属性** | 少 1 攻或少 1 防就会去世 ⇒ 只能重打 | 粽塔：0 绿第三章煮人幽靈（这区的攻防调整**只能在商店升级前**调整）；王大锤的历练：0F 打退化的时机不对，21 层才发现被坚固怪卡了属性 |
| **卡经验** | 打到后面才发现漏了经验 | 境界塔常见 |
| **卡门** | 以为红门可以咸（绕过去），或某些红门可以先开，结果红门挡路 | 精灵世纪少女；证道：「被亡魂镇 boss 层的 3 红门卡掉的玩家已经多到不想数了」 |

**「迪」**（同帖）：

> 除了卡红，有一种奇怪的现���叫"**迪**"，就是**明明没怎么咸黄，但是黄快用光了，
> 蓝却还有很多把**。令玩家只能**硬花掉一些蓝来存黄**，感觉亏死。

> **「迪」的本质是钥匙的"色相流动性"坏了**——玩家被迫做"用蓝换黄"的套利，
> 这是纯粹的摩擦而不是决策。

### 6.6 显伤 NPC：给了伤害数字就得给暗示

tid=1183 8–10 楼：

> 有的塔有带**显伤**的 NPC（甚至和这些 NPC 对话是过关必须的），
> 但是玩家会看到显伤认为这是打不过的怪物然后无视它。

作者（永葆一颗童心）的处理原则：

> 通常来说遇到这种 NPC 都需要作者**通过布局、素材搭配等因素给出足够明显的暗示**，
> 让玩家一眼就能发现这里不对劲。**如果做不到这一点，乃至误导玩家，就别做这种显伤 NPC。**

同帖还有一句对本项目很关键的社区共识（落葉的三月）：

> **值得庆幸的是，H5 上极少有能跟打不过的怪开战的塔了。**

⇒ **"打不过就不让打"在 H5 魔塔里是社区惯例，不是缺陷。**
本仓库的 `TOWER_STATUS_TOO_STRONG` 门禁其实是**符合社区惯例**的；
真正的问题不是这个门禁本身，而是**这个门禁之外没有任何别的代价**——
战斗既不能输，也没有别的风险，于是它退化成过路费。
详见 `gameplay-improvements.md`。

## 7. 提交前必须跑的校验

```
□  1. 上下楼楼梯不同格，且上下楼位置在层间的"相对位置"有变化
□  2. 上楼点与下楼点曼哈顿距离 ≥ 2 格
□  3. 每层 墙 42%–52%，空地 12%–22%，物件 30%–40%
□  4. 无 4×4 窗口内有效物件 ≤ 2（boss 层除外）
□  5. 无 5×5 窗口全满（强怪奖励区除外）
□  6. 每层 钥匙数 ≥ 必开门数 且 ≤ 门数 + 2
□  7. 全塔 总钥匙/总门 ∈ [0.90, 1.15]
□  8. 红钥匙数 < 红门数
□  9. 无"傻瓜门"
□ 10. 无闲置怪 / 无同质怪并列
□ 11. 每扇绕怪门后 3 层内能得到等效收益
□ 12. 每层至少 1 种"血厚可磨"和 1 种"脆但疼"的怪
□ 13. 至少 1 层：楼梯在环廊对角（强制穿越）
□ 14. 至少 1 层：0 门纯战斗；至少 1 层：0 怪纯奖励
□ 15. 存在 1~2 处"必须回头"的资源断点
□ 16. 隐藏层不可被传送跳过
□ 17. 战斗力回放：全塔最优路线 vs 最差路线，HP 差值落在设计区间内
□ 18. 楼层表生成后跑 `tools/analyze_maps.py --check`，输出与本节预算一致
□ 19. 【堆水空】无 0 伤怪（闲置怪），且正常流程下玩家至少需要权衡取宝路线
□ 20. 【堆水空】无 ≤1 只怪的水层；水层在一个区域内只占极少数
□ 21. 【堆水空】镜像对称楼层 ≤ 20%；同一楼层平面不被两层以上复用
□ 22. 【堆水空】堆的严重性排序：堆怪 < 堆道具 < 堆门 < 堆空地 < 堆墙
□ 23. 【黑海】无"时空离散性"：没有像素级/亚秒操作，没有挂机时移动的 NPC
□ 24. 【黑海】无"信息透明性"陷阱：暗墙/初见杀/前景层遮挡，要么明示要么不做
□ 25. 【黑海】无强制低速移动 / 强制不可快进过场
□ 26. 【数值】无"全是史莱姆"式同质化；后期怪物 DEF 高于玩家 DEF 上限（防无脑防杀）
□ 27. 【数值】无血限的高层塔不出现吸血/自爆
□ 28. 【数值】"迪"检查：最优路线下黄钥匙不该快用光而蓝钥匙大量剩余
□ 29. 【卡】不会出现卡属性（少 1 攻/1 防即死）
□ 30. 【卡】不会出现卡门（红门挡路且无法绕行）
□ 31. 【录像】通关路线不依赖"停在楼梯上 / 非顺时针 90° 转身 / 瞬移到相邻格"
□ 32. 【显伤 NPC】若 NPC 带显伤且必须交互，必须有明显的布局/素材暗示
```

> 第 19–21 条已由 `tools/analyze_maps.py` 自动实现（连同前面的 11 条，共 14 条自动检查）。
> 第 22–32 条多数需要人工判断，但写下来能防止遗漏。
> 全部来自社区三篇帖子：tid=1183《新人造塔避雷指南》、tid=1052《拒发审核简易指南》、
> tid=241《无意义阻击夹域网》、tid=210《如何造爽塔》。

| 每层有"血厚"与"脆但疼"两种怪 | 是 | 6 层只有 2 种怪，10 层只有 2 种 | ⚠️ |

| **水层（≤1 只怪）** | 0 层 | **第 3、4 层** | ❌ |
| **镜像对称的层** | ≤ 20% | **7/10**（3, 5, 6, 7, 8, 9, 10） | ❌ |
| **楼层平面复用** | 不复用 | 10 层只有 **7 种**平面；**5/8/10 共用**，**7/9 共用** | ❌ |
| **闲置怪（0 伤怪）** | 0 只 | **4 只**（1F 史莱姆 / 7F 法师 / 9F 石魔 / 10F 怨灵） | ❌ |
| **战斗占回合比** | > 10% | **3.0%**（17 场 / 568 回合） | ❌ |

**14 条自动检查里只有 3 条通过。**

**结论：十层塔的骨架是稳的（钥匙/门总数比 1.08 落在健康区间，
空地占比也达标），但空间形态、楼梯惯例、敌人密度、物件密度、
红钥匙稀缺性、水层、对称性、平面复用、闲置怪、战斗占比这十条全部不合格。**

其中**「7/10 层镜像对称」和「5/8/10 三层共用同一个平面」是最刺眼的两条**——
按 tid=1052《拒发审核简易指南》的说法，**对称既是绘制手段也是"水层"手段**，
而本项目把同一个平面用在了三层上，只是往里面填了不同的道具和怪。
详见 `docs/research/gameplay-improvements.md`。
