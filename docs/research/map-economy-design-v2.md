# 地图设计二轮研究：用战斗临界点组织楼层，而不是堆格子

**研究状态：提案与可复算数值分析；不修改任何地图或游戏规则。**
这份研究叠在 [PR #4（关卡分支审计）](https://github.com/Wzdhehe/mosaico-magic-tower/pull/4) 之上；#4
基于 [PR #1（手工地图）](https://github.com/Wzdhehe/mosaico-magic-tower/pull/1)。
[PR #2](https://github.com/Wzdhehe/mosaico-magic-tower/pull/2) 提供原始研究和探针。
**暂时不设计存档迁移、不扩充地图、不要求重新绘制美术。**

## 1. 目前真正致命的缺陷是“整体经济没有和地图联动”

战斗公式直接来自 \`main/tower.c\`：每次伤害
\`(ceil(敌人HP/(英雄攻击-敌人防御))-1) * max(0,敌人攻击-英雄防御)\`，
前提为英雄攻击大于敌防。

| 变量 | PR #1 参考胜利回放，Boss 前 |
|---|---:|
| 英雄 HP / ATK / DEF | 921 / 72 / 37 |
| 金币 | **229**（已扣除尚未获得的 Boss 奖励 150） |
| Boss HP / ATK / DEF | 700 / 58 / 46 |
| 未购物的 Boss 伤害 | 546 |
| 商店加点 | 15 金币换 +3 攻或 +3 防 |
| **再买 7 次防御** | **花 105 金币，防御到 58，Boss 伤害变为 0** |

用 \`python tools/audit_shop_breakpoints.py\` 可从实际 C 源码、头文件、
\`tests/win_route.json\` 复算：金币计算**不**把打败 Boss 之后才能拿到的
150 金币算作可提前消费的钱。

### 固定一笔预算，只看 Boss

| 购物策略 | 消费 | 对 Boss 损血 | 说明 |
|---|---:|---:|---|
| 不买 | 0 | 546 | 回放基准 |
| 攻 +3 | 15 | 504 | 攻击越过一部分回合阈值 |
| 防 +3 | 15 | 468 | 本点位防御更有效 |
| 攻 +12 | 60 | 378 | 保持原 DEF |
| 攻 +6 / 防 +6 | 60 | 315 | 均衡 |
| 防 +12 | 60 | **234** | Boss 专项更省血 |
| 防 +21 | 105 | **0** | 所有普通攻击均被防御归零 |

**这是一个条件推演，不是新的通关录像。** 假设玩家可以从已通的楼层
返回二层商店再爬回去，且没有任何未计入的途经消耗。现有程序的商店
不限制购物次数，现有地图允许回溯；但本研究没有逐步重放“返回购物”路线。

### 应当先决定经济设计哲学，再改任何 Boss 数值

- **不能只把 Boss 攻击从 58 调高几倍**：那通常只会抬高必须买防御的门槛。
- **不要直接上“破甲 Boss”**：指南第 12–14 页讨论了过度反制使玩家加点无意义的问题。
- 优先让**购物的机会成本**真实存在：较早买防御会牺牲攻击带来的回合阈值收益；
  商店定价/购买容量是否变化，要和下一两层的守卫一起设计与测试。
- 至少保留两种可以过 Boss 的经济路线：攻先/防先；不要规定唯一正确加点。
- 在当前状态下，长距离回二层购物的**输入操作成本**可能是唯一阻止“零损血”的机制；
  不应把枯燥的跑图当作数值平衡设计。

## 2. 以“角色属性断点”安排资源，形成可预判的选择

以第 9 层附近 ATK=62, DEF=28 的参考情境为例，伤害来自
\`tower_enemy_preview\` 的同一公式：

| 怪物 | 当前 | 先取 1 攻宝石 (+5) | 先取 1 防宝石 (+3) |
|---|---:|---:|---:|
| 石魔 Golem (180/30/16) | 6 | 6 | **0** |
| 怨灵 Wraith (260/36/22) | 48 | 40 | **30** |
| 魔王 Demon (700/58/46) | 1290 | 990 | 1161 |

注：Boss 此处只是说明属性变化的灵敏度；角色当下 HP
和后续可拾取补给并没有纳入比较，不是说第 9 层就应该能打 Boss。

这一组数值说明：在这一档属性下，蓝宝石（防御）对石魔和怨灵
更直接；但越临近 Boss 的攻击阈值，攻击提升可能一次省下数回合伤害。
可据此让玩家**提前 1–2 层选择宝石，下一层就看到不同回报**。

第 9 层现有两条通过不同守卫的路，但 #4 已确认两路最终能拿到同一批
奖励。正确的优化方向不是再堆怪，而是给**分支的资源取得顺序**设置
实际影响：例如先取攻宝石可以减少后续高防怪轮数，
先取防宝石可以降低当前守卫的损失，二者都能通关但路径/耗血不同。

## 3. 逐层“设计任务书”（不是立即改图）

| 楼层 | 玩家应当作出的判断 | 必须能看到的反馈 | 研究/制作要求 |
|---|---|---|---|
| 1F 门厅 | HP 与钥匙分别如何支付成本 | 初见伤害可预估，黄门可解释 | 保留新手引导；哨兵的不可破坏提示待单独修 |
| 2F 商人厅 | 商店 +3 攻/+3 防哪个能改变下一战 | 买完后预览数值确有变化 | 商店收益/定价与后续敌人预算联动，不要无限轻易免疫 |
| 3F 幽灵回廊 | 蓝门后的红钥匙是否值得回头取 | 5F 红门提前有明确线索 | 蓝门守护价值可量化，避免信息陷阱 |
| 4F 兵营 | 拿蓝钥匙还是先拿支路补给 | 3F 密室真正可开 | 允许安静的零怪谜题层，不硬加怪物 |
| 5F 封印书库 | 开红门推进与可选战斗哪个合算 | 宝石收益在 6F 可被体会到 | 红门不能几何绕过；给侧室设置明确代价 |
| 6F 废墟 | 高攻/高防路线如何影响守卫损失 | 本层先后击怪损血确实不同 | 减少 39 格空地的无意义往返，不必填满 |
| 7F 礼拜堂 | 打怨灵取得红钥匙的代价 | 8F 红封印可见、可理解 | 必须保留“怨灵守钥匙”的拓扑约束 |
| 8F 牢房 | 红钥匙与可选补给的取舍 | 9F 可比较两个守卫 | 在此作第一次 Boss 前资源预告 |
| 9F 王座前厅 | 石魔/怨灵成本不同，先取攻还是防 | 10F Boss 损血随选择明显变化 | 两种路线均可过关，不是装饰性岔路 |
| 10F 魔王王座 | 是否值得回补资源/购物再战 | 战斗前显示预估伤害与剩余 HP | 避免“无限低价防御 = 免疫”让终局无意义 |

如果以后加层数，**先验证新的楼层承担了不可替代的决策功能**；
“多一层”本身不是价值。11×11 小屏在当前仍优先让走路动作少，
分支信息直观；大地图/镜头箭头留作独立功能。

## 4. 不使用“通关血量百分比”假装有了复玩性

参考全通关路线只能说明**有一种顺序可通关**，不能说明有多少
真正不同的选择。建议关卡设计的下一次实作验收至少比较：

1. **攻优先线**：尽早买攻击，测试跨越哪些敌人回合阈值；
2. **防优先线**：量化即时损血减少与 Boss 是否过早无伤；
3. **钥匙节约线**：避免某些可选门，比较留下的备用钥匙、
   少取宝石所付出的 HP 和可达性。

每条路线用**完整 C 模型回放**记录地图状态、拾取顺序、伤害、
金币消耗和卡死点。不要只以“最终 HP 最少 2–4%”为目标：这可能
诱导只允许唯一正确路线，与复玩性背道而驰。

### “硬错误”与“设计警告”分离

**硬错误**：楼梯不可达、钥匙被自己锁住、红封印可以直接绕过、
某条指定为可行的路线实际卡死、战斗公式与 C 不同。

**设计警告**：可走格太空、全层怪物数量过低、两条路只产生微弱
步数差异、玩家金币囤积、商店轻易清零 Boss 伤害。
后者必须由设计师判断是否合理，不能任意当做 CI 失败。

## 5. 后续实现的最小顺序

1. 在现有 11×11 内设计并审计**9F→10F 两种资源路线**；
   先证明不同加点在 9F/10F 的战斗结果，不加新怪物特技。
2. 同步校准商店价格/增益或购买约束，但必须考虑 2F 商店
   可以通过跨层回溯反复访问；不要靠让玩家厌烦跑图来“封印”强度。
3. 调整 6F 的岔路价值和 3F–5F 的可选收益，增加 1 个
   由已有门钥匙/NPC 文本实现的**微谜题**。
4. 测试至少两条完整跨层策略路线；优先证明无“误买一次就废档”
   的软锁死。失败体验在后续单独讨论，不依赖存档迁移。
5. 最后再考虑更多层数和大地图视角，不提前引入帧绘制负担。

## 6. 复现、证据与局限

运行：

\`\`\`sh
python tools/audit_shop_breakpoints.py --check
python -m unittest discover -s tests -p test_shop_breakpoints.py
python tools/audit_tower_decisions.py --check
python tests/run_tests.py --label economy-study
\`\`\`

新脚本纯宿主机工具，不运行在 Mosaico 上，不向游戏二进制加入任何算法。
它从 \`main/tower.c\` 解析 Boss 四项属性，从 \`main/tower.h\` 获取商店单价、
加点量，从 \`tests/win_route.json\` 得到一条经校验的成功路线。
它没有证明玩家会如何购买，也没有证明最优全塔解。真正平衡修复应当
作为独立后续 PR，并逐条留下可执行录像证据。
