# Battery acquisition: RC4 field correction

The RC3 adapter omitted the official BQ27220 profile initialization and replaced SOC with 100 whenever FC was set with non-negative current. FC is a status alarm, not a percentage. That override could fabricate 100 before revealing the gauge's much lower SOC. The user's long charging/stuck reading still requires raw hardware evidence; a UI fix alone does not establish accurate fuel gauging.

## References inspected

- Factory backups `D:/espbulid/espclaw_backup/factory__0x20000.bin` and `espclaw_backup_v04/factory__0x20000.bin`: include battery-monitor initialization, BQ27220 profile-write and full readback-verification paths. Their binary strings do not establish exact application logic or matching profile parameters.
- User-provided Ideas firmware `D:/0e257e8f-61a0-4306-979d-d578722d4d1c.irisfw`, release 1.0.5, SHA256 `90ddd31a26170abff250efd2133cc59fa0083e4cc2c46a1ed761af2a8f6356c2`: all manifest component checksums match. `ota_0.bin` contains the official BSP battery attach/read/initialization strings and the complete 50-byte `parameter_cedv_t` matching the pinned BSP at file offset 403804. This includes the 80mAh interim profile and EDV0/1/2 of 3000/3410/3530mV. No code from the other application was copied or executed.
- Owning source: official workspace `submodule/esp-mosaico-bsp/components/esp-mosaico-bsp/onboard/battery.c`, `bsp/battery.h` and the pinned `espressif__bq27220` component. `bq27220_create` verifies matching parameters without overwriting learned capacity; mismatches use its supported RAM update, readback verification and resealing.
- [BQ27220 TRM](https://www.ti.com/lit/ug/sluubd4a/sluubd4a.pdf), standard commands 2.6–2.10, 2.21, 2.27–2.28. [Board guide](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32s31/esp-mosaico/user_guide_v1.0.html) lists a nominal 65mAh cell. The BSP explicitly calls its 80mAh profile interim; using the official profile is not a claim of individualized calibration accuracy.

## Ownership and behavior

`game_battery_create` borrows the shared BSP I2C bus, attaches its checked reader, logs a pre-init raw sample, performs up to three safe DEVICE_NUMBER queries (20ms gaps, requiring type0220), and calls `bsp_battery_init` once. The first query NACKed on the actual device; the later official query succeeded. No application profile writes are attempted without confirmed identity. It never defines its own gauge parameters, triggers calibration/reset/OCV, writes OTP or changes the charger. The BSP singleton remains borrowed for the application lifetime; deleting the adapter only removes its own device attachment.

Every five seconds, checked 10ms reads obtain Voltage (08), BatteryStatus (0A), Current (0C, signed), RemainingCapacity (10), FullChargeCapacity (12), SOC (2C), OperationStatus (3A) and DesignCapacity (3C). Invalid I2C data, missing battery, incomplete/config-update state, implausible small-cell capacities/voltage or contradictory SOC/capacity reject the sample. Whole-mAh capacity rounding and a one-second gauge update boundary allow a three-point discrepancy.

Each scheduled poll makes at most two complete attempts, with a fresh zeroed snapshot for each. No retry sleep is added. If neither is valid, the display may retain the last validated percentage and charge/discharge appearance for strictly less than 15 seconds from its successful sample. A failure never renews that timestamp. At 15 seconds the output becomes unknown (`--`), even if scheduling jitter has deferred the next I2C poll; that one-shot expiry output makes no hardware reads. Before any good sample, failures remain unknown. Successful recovery replaces the cache immediately with the actual validated SOC, without clamping jumps or inventing a voltage-derived value. Cached appearance can lag a physical plug/unplug until a valid sample arrives, for at most the same 15-second lifetime.

Valid percentages are the gauge's SOC, without FC replacement or voltage-to-percentage extrapolation. Positive instantaneous current takes precedence over a stale DSG flag and is green. At zero current, DSG clear remains green for charging/relaxation without requiring FC. Negative current, zero-current discharge mode or charge inhibit is white. The display has no lightning. This is battery charge/discharge-mode classification, not an independent physical USB-presence detector.

Polling is owned by the existing UI task. No extra task, animation, persistent battery state or save writes are introduced. Scheduled samples use the five-second cadence, with only the bounded second attempt on rejection; unchanged display values do not request a frame. Each transaction has a 10ms timeout and the first failed transaction ends its attempt, so a failed poll has at most 16 transactions and 160ms of configured transaction timeouts (not a measured end-to-end latency). Raw telemetry logs on the first sample, validity changes, successful retry, charge/discharge state changes and once per minute. Each rejected attempt logs the failing register/ESP error or validation reason, last-good age and raw V/I/SOC/RM/FCC/DC/status/op. During the first 15 seconds only, invalid post-init polls use a one-second cadence; valid samples immediately resume the five-second cadence. No routine idle-loop log is added.

## Evidence and limits

`tests/run_battery.py` compiles the real adapter against a fault-injecting I2C/BSP port. It covers official init, failed init cleanup, checked register whitelist, SOC9 plus stale FC, actual full SOC100, positive/negative current, inhibited charging, absent battery, read failures, uninitialized/config-update state, zero FCC, invalid voltage, default multi-Ah profile, contradictory capacities and five-second idle read suppression. Transient coverage includes one failed SOC transaction, one inconsistent SOC snapshot, both-attempt failure, diagnostic register/error/reason, a non-renewing cache, exact expiry with scheduling jitter and no extra I2C, unknown startup and unclamped recovery.

Hardware acceptance must retain pre/post-init diagnostics and a real charge/discharge sequence. No host test, green icon or single plausible percentage proves accuracy or battery health. Do not add guessed voltage curves, percentage clamps or destructive battery cycling to hide remaining discrepancies.

## Real-device findings, 2026-10-19

Device4553502d4952495301001c2904d0bc08 initially returned V4180mV/SOC9/RM257/FCC2872/DC0/op0000. Initial BSP attach failed on its first identity packet with ESP_ERR_INVALID_RESPONSE. A subsequent diagnostic boot confirmed type0220 and found a gauging-config mismatch (expected3345, actual4138). The official component wrote eight RAM blocks, verified all26 fields, confirmed CONFIG UPDATE exit and resealed. It then reported V4178mV/SOC100/RM80/FCC80/DC80/op00a6. The first immediate post-init register set was stale; the next poll was consistent. This confirms the missing/mismatched gauge configuration on this device; long-term accuracy still needs real charge/discharge observations. No guessed percentage was substituted.

The user unplugged/replugged USB: the battery turned white after several seconds, but initially stayed white after replugging. The retained trace had I=+19mA with status4029 (DSG still set), then I=+17mA/status4028. RC4 was corrected to prioritize positive instantaneous current over the lagging mode bit; the real +19mA/DSG-set sample is now a regression test. The hardware charge LED stayed warm-colored at SOC100; [the official Mosaico guide](https://mosaico.espressif.com/zh/guide/) says white denotes charging completion. SOC100 is a capacity estimate, not proof of charger termination; the model does not cap it to99 or fabricate an end-of-charge event.

Later field play showed 97%, a temporary `--`, then 97% again. Post-plug samples were valid (for example4196mV/+28mA/SOC99/RM79/FCC80/DC80/op00a6), with the same boot and crash_count0. The critical invalid sample was not retained: repeated touch-driver warnings crowded the log buffer and dropped-byte count increased. The hardware failure cause is therefore unconfirmed. The tolerance and diagnostics above address display continuity and future evidence; they do not establish a repaired I2C bus or calibrated long-term accuracy.

Offline disassembly of the supplied1.0.5 package traced `bsp_battery_read` at0x5011211e, SOC getter0x50116dc2 reading0x2c, application retry at0x50016688/0x50016690, and cached fallback at0x50016898 on repeated full-read failure. Its SOC-to-text path formats `%d%%` directly. This confirms the reference also uses gauge SOC and a cached fallback; it does not prove all scalar register failures are detected, or that its estimator is more accurate. No third-party code is copied or bundled.
